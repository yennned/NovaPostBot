# E2E-харнесс

Прогон настоящих `Update` через настоящий `build_dispatcher` — на живой БД, с
живыми НП и Google Sheets. То, чего не видят юнит-тесты хендлеров.

## Зачем

Юнит-вызов хендлера скрывает два самых частых класса дефектов:

- **ошибку сигнатуры** — aiogram передаёт событие первым позиционным аргументом;
- **падение в теле** — aiogram пишет трейс в лог и **молча ничего не отвечает**;
  для пользователя это «кнопка не реагирует» (`18b1995`).

Отсюда главный детектор харнесса: **ноль исходящих вызовов на тап = дефект**.

Тем же способом уже находили `802022a` (тап меню в состоянии поиска «съедался»),
`d964aee`, `78d2453`.

## Состав

| Файл | Что делает |
|---|---|
| `env.py` | поднимает окружение стенда (`.env.prod`) **до** импорта `app.*`; подменяет Redis на локальный |
| `lib.py` | `RecordingBot`, `Screen`, `Persona`; тап по **видимому тексту** кнопки, замер латентности, детектор молчания |
| `human.py` | «человеческий шум»: опечатки, двойные тапы, мусор в поля, откаты, паузы |
| `crawler.py` | обход всех кнопок роли: нижняя панель → BFS по inline-клавиатурам |
| `cascade.py` | каскад ТТН + общий на все процессы бюджет реальных документов НП |
| `run_persona.py` | запуск одной персоны (один процесс) |
| `preflight.py` | доступы, валидация ключей НП, срез «до» |
| `validate.py` | **единый** отчёт по всем персонам + сверка с НП + уборка |
| `restore_names.py` | откат данных, затёртых обходом (см. «Грабли») |
| `prod_health.py` | после деплоя: боевой процесс реально поллит Telegram (`409` = жив, см. ниже) |
| `price_probe.py` | сверка объёмного веса с боевым тарифом НП (**только чтение**, ТТН не создаёт) |
| `insured_probe.py` | оголошена вартість: выводится из корзины и доезжает до НП полем `Cost` |

### Сверка объёмного веса (`price_probe`)

Бот считает объёмный вес локально (`объём м³ × 250`) и шлёт в `getDocumentPrice`
`Weight = max(фактический, объёмный)` — потому что габариты сами по себе в оценку
не уходят. Коэффициент **опубликован** в тарифах НП
([novaposhta.ua/shipping-cost](https://novaposhta.ua/shipping-cost/)), проверять его
незачем. Пробник проверяет проводку: что габариты пресета доезжают до запроса, что
берётся именно максимум и что цена совпадает с той, которую НП даёт за те же
габариты. Показывает по каждому пресету цену за «голые» 2 кг и за тарифный вес.

```bash
.venv/bin/python -m scripts.e2e.price_probe --profile "<назва ФОП>" --city Львів
NP_PROBE_API_KEY=<ключ> .venv/bin/python -m scripts.e2e.price_probe  # без БД
```

Ключ берётся из БД по названию ФОП либо из `NP_PROBE_API_KEY` (переменная
окружения или строка в локальном `.env`) — в вывод он не попадает, печатаются
только последние 4 символа. Если колонка «стало» разойдётся с тарифом НП за эту
вагу — правится одна константа `VOLUMETRIC_KG_PER_CUBIC_METER` в
`app/novaposhta/mapping.py`, логика не меняется.

### Оголошена вартість (`insured_probe`)

Сумма выводится из стоимости корзины и уходит в НП полем `Cost` — это и предел
возмещения, и база страхового сбора. Пробник проходит поток настоящими `Update`
до карточки и проверяет, что сумма не нарисована, а реально меняет тариф.

```bash
.venv/bin/python -m scripts.e2e.insured_probe --list          # кто с ценами в «Складі»
.venv/bin/python -m scripts.e2e.insured_probe --run-id ins1 --as-user <tg> --count 5
.venv/bin/python -m scripts.e2e.validate --run-id ins1 --cleanup --keep 0
```

**Сравнивать надо на сумме выше 500 ₴.** По тарифам НП комиссия считается «від
оголошеної цінності до 500 ₴», поэтому на 200–300 ₴ сбор нулевой, цена не
меняется, и прогон не отличает «сбора нет» от «сумма не доехала». Пробник поэтому
правит сумму на 10 000 ₴: замер на боевом дал 200 ₴ при нуле и 250 ₴ при 10 000.

### Проверка прода после деплоя

```bash
.venv/bin/python -m scripts.e2e.prod_health   # ~40 с: держим длинный getUpdates
```

Зелёный `deploy` в CI не означает «бот работает»: снимок `docker compose ps`
делается через секунду после старта, и «Up Less than a second» одинаково выглядит
у поднявшегося контейнера и у падающего на первом обращении к БД.

**Направление конфликта у Telegram обратное интуиции.** При конкуренции за токен
обрывается тот, кто поллил *раньше*, а новый запрос обслуживается. Поэтому
короткий пробник получает `200 OK` независимо от состояния прода. Пробник сам
встаёт в длинный поллинг и ждёт, когда его вытеснит боевой процесс: **`409` —
это успех**. Боевому поллингу это не вредит — aiogram ловит любую ошибку
`getUpdates` и продолжает с backoff.

Коды возврата: `0` — жив, `1` — не поллит, `2` — **не знаю**. Третий код не
формальность: `409` доказывает живость только в режиме long polling, а при
включённом вебхуке тот же ответ придёт и от погашенного контейнера — поэтому при
непустом `url` в `getWebhookInfo` пробник даже не пробует поллить. Сбой связи у
самого пробника тоже даёт `2`, а не `1`: собственная ошибка не должна выглядеть
как авария прода.

## Как гонять

```bash
# 0. доступы стенда (секреты в чат/лог не попадают)
ssh novapostbot 'cat ~/NovaPostBot/.env' > .env.prod && chmod 600 .env.prod

# 1. preflight: ключи НП валидны, срез «до» снят
.venv/bin/python -m scripts.e2e.preflight

# 2. обход всех кнопок роли (одна персона = один процесс)
.venv/bin/python -m scripts.e2e.run_persona \
    --run-id run1 --name client-owner --telegram-id <ваш dev id> \
    --as-user <telegram_id клієнта> --seed 5 --max-taps 90

# 3. каскад ТТН — несколько процессов, общий бюджет
.venv/bin/python -m scripts.e2e.run_persona --run-id cascade1 \
    --name worker-a --telegram-id <ваш dev id> --as-user <telegram_id працівника> \
    --scenario cascade --ttn-budget 4 --global-limit 10 --seed 101

# 4. один отчёт на всё + уборка (1–2 ТТН оставить на проверку)
.venv/bin/python -m scripts.e2e.validate --run-id cascade1 --cleanup --keep 2
```

`--global-limit 0` — холостой прогон: сценарий доходит до карточки и отменяет,
реальных документов НП не создаётся. Так обкатывают изменения в `cascade.py`.

## Правила, которые нельзя нарушать

1. **Один процесс — одна персона.** Роутеры в `app/bot/handlers` — модульные
   синглтоны; второй `build_dispatcher` в том же процессе падает с «Router is
   already attached». Побочная выгода — настоящая конкуренция к Postgres/НП/Sheets.
2. **Обход не трогает чужие данные.** Разрушающие `callback_data` — в
   `crawler.DESTRUCTIVE`, свободный текст вводится **только** в поисковые поля
   (`crawler.SAFE_TEXT_INPUT`).
3. **Персоны не выносят вердиктов.** Они пишут сырой JSONL; «зелено/красно»
   решает только `validate.py` — иначе каждая мерила бы успех по-своему.
4. **Исходящие Telegram — в чат владельца.** `RecordingBot` в режиме `real`
   переписывает `chat_id` на `env.outbox_chat_id()` (первый `DEV_TELEGRAM_IDS` или `E2E_OUTBOX_CHAT_ID`). Реальные клиенты тестовых
   сообщений не получают. В режиме `stub` наружу не уходит ничего — он нужен
   каскаду, где per-chat лимит Telegram (~1 сообщение/сек) исказил бы замеры.

## Грабли (оплачено боевым прогоном)

- **Обход переименовал реальных клиентов.** На первом прогоне краулер вводил
  мусор в любой экран, ждущий текста, — включая «✏️ Змінити ПІБ» и правку полей
  ФОП. Пятеро клиентов стали «зжзж», у двух ФОП затёрлись `name`/
  `sender_full_name`/`edrpou`. Данные восстановлены `restore_names.py`, причина
  закрыта денилистом и `SAFE_TEXT_INPUT`. **Мораль:** на боевом стенде «мусор в
  поле» — это запись в чужие данные, а не проверка экрана.
- **Бюджет ТТН тёк под гонкой.** `flock` снимался до того, как буфер файла
  уходил на диск, и соседний процесс читал усечённый JSON. Лечится `flush` +
  `fsync` до `LOCK_UN`; регресс закрыт `tests/bot/test_e2e_lib.py`.
- **Боевой воркер живой** и реагирует на созданные прогоном ТТН: трекинг и
  SLA-таймер (30 раб. минут) шлют уведомления **со своего процесса**, мимо
  перенаправления. Либо укладываться в окно и чистить сразу, либо гасить воркер.

## Что харнесс не проверяет

Персоны ходят через `/as_user` (god-mode бота), а `app/bot/permissions.py`
проверяет dev **первым** — значит **отказы по правам этим способом не
проверяются**. Для них нужен вход своим `telegram_id`.
